## 这次要解决什么

M2 已具备页面与加密内核，但页面使用固定演示数据：输入口令不会真正解锁，添加、编辑、删除也不会保存。用户希望继续完成基本可用的 Android 内测版，通过安装 APK 在自己的手机上验证，再反馈问题。

交付方式已由用户确认：开发者在 Mac 上开发和自动测试，提供 APK；用户安装到手机后测试。真机无需始终连接电脑。M3 的设备验收仍需完成，但不作为开始开发和交付内测包的前置条件。

## 计划交付的使用流程

1. 首次打开创建真实加密库，可设置恢复口令；跳过时进入有明确警告的设备绑定模式。
2. 手动输入、相机扫码或从图片导入账号；列表生成真实验证码并计时，可搜索、编辑、删除和排序。
3. 设置口令、生物识别、自动锁定、隐藏验证码和剪贴板清理；锁定后不能继续读取库内容。
4. 使用系统文件选择器导出加密 `.2fab`，导入时校验口令、预览并选择合并策略；恢复后重新建立本机加密库。
5. 在手机上验证上述闭环；未实测的硬件能力明确列为待验证。

## 需要明确的密钥行为

v1 库的口令包装 AAD 包含库 nonce，因此每次保存生成新 nonce 时，需要重新认证口令包装。恢复口令在派生后立即擦除；解锁会话只保留 DEK 与派生的 KEK，锁定时擦除。生物识别模式需要用要求每次强认证的 Keystore 密钥包装会话密钥材料，才能在不重复输入口令的情况下安全保存。该平台本地信封不进入备份，也不改变 `vault.bin` / `.2fab` v1。

平台本地包装采用 DataStore；文件提交使用 AtomicFile，并显式同步、读回比对，只有确认目标文件实际更新后才推进内存状态。项目既有威胁模型继续适用：外部 URI、图片和备份必须有大小限制；认证失败不修改现有库；不输出含密钥的错误信息。

## 实际实现与审查修复

真实库与界面已接通。手动输入支持 SHA1/256/512、6/8 位和 1–300 秒周期；完整 otpauth 链接保留其中的参数。相机或图片识别后进入确认添加页面，不会直接打开二维码中的地址。列表每秒更新真实验证码，详情支持编辑、删除与上下移动顺序；不再显示密钥种子。

备份通过系统文件选择器读写，不申请存储或网络权限。输入备份限制 12 MiB；二维码图片实际读取限制 16 MiB，解码边长限制 2048，避免直接把任意大图片加载到内存。导入前预览，三种合并策略和替换操作都已接线；替换需要二次确认。

审查中发现并修复了这些问题：

- **保存成功的判断不够可靠**：Android AtomicFile 的提交可能只记日志而不抛错。现在显式同步并读回比对，避免界面说已保存、实际上还停留在旧库。
- **口令更改后清理失败容易误导用户**：库已提交后，清理旧设备包装若失败，不再把已完成的口令修改或导入显示成普通失败；旧包装仍受当前盐、KEK 和 DEK 校验约束。
- **锁定与异步结果竞争**：后台锁定会取消在途认证，旧会话的解锁、导出或预览结果不能重新打开页面。密钥清理与文件操作在同一串行边界执行。
- **系统选择器和页面重建**：文件/图片结果带会话身份与绝对超时，旧会话结果丢弃。导出密文和导出时的库版本随 ViewModel 保留，避免旋转后静默生成空备份或误标另一个版本已备份。
- **跨 App 复制过早被清空**：去掉退出前台立即清剪贴板的行为。后台锁库仍清除库密钥；验证码按剪贴板设置保留短暂粘贴窗口，手动锁定仍立即清理（ADR-024）。
- **旧系统设备密钥丢失风险**：根据 Android 官方已知缺陷，unlockedDeviceRequired 仅在 API 35+ 启用，旧版本在设备密钥入口检查锁屏状态（ADR-023）。StrongBox 生成失败回退普通 Keystore，硬件安全等级仍需真机确认。

界面继续复用 Quiet Ink tokens。排序暂用详情上下移动，登记 EX-005；中文文案沿用 EX-002，M4 再做完整多语言。没有加入云同步或后台联网。
