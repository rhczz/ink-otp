# 隐藏复制修复与无恢复口令锁定核查

## 为什么做

用户试用 [0.4.1](2026-11-17-phone-feedback-fixes.md) 后发现：开启隐藏时点击验证码会显示数字；手动锁定后点解锁直接进入，没有新的指纹/手机凭据验证。用户已确认未设置应用恢复口令，并追问恢复口令用途。核对后，用户明确要求无恢复口令模式维持现状，不新增系统认证；因此本次只修隐藏复制，认证仅记录调查结论，保留旧账号、既有格式、Quiet Ink 组件与离线边界。

## 实施前范围与验收

先同步设计 §11.7 及 [交互规格](../../spec/android-interaction.md)。列表和详情删除临时显码状态；首击及连续点击复制真实码但视觉/无障碍始终隐藏。仅关闭隐藏设置才恢复显示，不修改认证或密钥包装。用户确认范围后，撤回无口令认证的设计草稿，未实施认证代码改动。

验收覆盖首击/连续复制成功、隐藏语义、详情进入和返回、周期刷新、开关变化、HOTP 不复制；沿用现有失败、取消、会话/锁定及升级用例。补先失败后通过的回归，按 Makefile 执行核心/App测试、实际行/分支覆盖率、构建、Lint、Python对拍和权限检查，再交付原签名、版本递增的 APK。手机实际剪贴板粘贴、TalkBack 和覆盖升级保持待测。

用户随后明确要求“修复、测试好之后直接发布”。本轮版本为 `0.4.2-beta.1` / versionCode 5；本机验证通过后提交修复、推送对应 tag、等待真实远端 CI/签名/发布，再下载并验证公开 APK 与校验和。不将本机通过或 tag 推送当作发布完成。

## 原来怎样与证据

`VaultListScreen` 的 revealed 集合让隐藏卡片第一次点击变为显示并提前返回，未真正复制；第二次才复制，TalkBack 也会随之读码。详情有另一套显码状态，因此进入详情仍可绕过全局隐藏。

`VaultViewModel` 初始化和 unlock 的无口令分支都直接调用 `unlockDevice()`。仓储只要求手机当前解锁的 DEVICE 密钥，不要求这次操作的新认证；锁定清掉内存，下次点击仍能取回库。这符合原设备绑定降级设计。用户了解恢复口令用途后，明确表示“这个不用补了，只有设置了恢复口令才需要系统认证”，因此保持既有行为，设置口令后的验证继续按现有生物识别/每次进入验证开关执行。

随后用户设置恢复口令并在手机实测，确认系统认证正常，明确表示第二项不需要修复。这一具体用户反馈记为已确认；没有机型/系统版本及完整专项过程，不能扩展为所有认证硬件路径或 M3/M4 全部验收通过。

恢复口令是用户另设的应用口令，用于口令解锁、备份导出和对应加密备份的恢复；App 不明文保存或上传它。恢复需同时具备备份文件与对应口令，旧备份不会随应用口令修改而改写。开启每次进入验证后，口令不能绕过系统认证。

用户也询问两个认证开关的区别。当前“生物识别解锁”遵守自动锁定时限，允许强生物识别或应用恢复口令；“每次进入时验证身份”在切出返回时强制系统验证，包含系统允许的生物识别/锁屏凭据，所以启用后禁用前一个模式。互斥来自本 App 的包装模式选择，非 Android 要求。此处只解释现状，不调整开关或策略。

## 实际改动与验证

列表直接使用原条目的 hidden 状态，删除首击临时显示分支；第一次及连续点击均把真实验证码交给现有复制路径。详情删除临时揭示状态、点击显码动作及提示，保留复制按钮，显示始终由隐藏设置决定。只有关闭设置才恢复显示；认证、剪贴板敏感标记/清理、存储及格式不变。
